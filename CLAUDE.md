# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`tft-platform` is a Teamfight Tactics stats site: a Go backend that ingests match data from the Riot API into Postgres, computes meta statistics, and serves a JSON API consumed by a React/Vite frontend.

## Commands

### Local environment
```bash
scripts/dev-up.sh                 # start Postgres (docker-compose) and apply all migrations
scripts/migrate.sh <name>         # create a new NNNN_<name>.up.sql / .down.sql pair in internal/db/migrations
```
Postgres runs at `postgres://tft:tft@localhost:5432/tft`. Migrations are applied by the `migrate/migrate` container in `deploy/docker-compose.yml`, not by Go code.

### Go backend
```bash
go build ./...
go vet ./...
gofmt -l -w .
go test ./...
go test ./internal/riotapi -run TestName   # single test
```
Tests that need Postgres (`store`, `ingest`, `apiserver`) skip unless `TEST_DATABASE_URL` is set; `scripts/dev-up.sh` creates the `tft_test` database:
```bash
TEST_DATABASE_URL="postgres://tft:tft@localhost:5432/tft_test?sslmode=disable" go test -race ./...
```
Each such test gets a fresh schema with all migrations applied (`internal/store/storetest`), so they're parallel-safe. Fake Riot responses go through `internal/riotapi/riotapitest`, which points a real `riotapi.Client` at an `httptest` server.
Running a binary requires env config (see `internal/config/config.go`):
```bash
DATABASE_URL="postgres://tft:tft@localhost:5432/tft" RIOT_API_KEY_FILE="deploy/.secrets/riot-api-key.txt" go run ./cmd/api
```
A malformed value (`RIOT_APP_RATE_LIMIT_PER_2MIN=1OO`) or a non-positive rate limit fails startup, naming every offender; an empty value counts as unset. Other env vars: `RIOT_API_KEY` (fallback when no key file), `RIOT_APP_RATE_LIMIT_PER_SEC` (default 20), `RIOT_APP_RATE_LIMIT_PER_2MIN` (default 100), `HTTP_ADDR` (default `:8080`), `SETDATA_SYNC_INTERVAL` (default `6h`, `0` disables the API server's set data sync), `DB_STATEMENT_TIMEOUT` (default `20s`; the API's Postgres pool cancels any statement running longer, answered as 503 `db_busy` with `Retry-After`; riotsync, the aggregator and ingestcli keep no timeout) and `DB_MAX_CONNS` (default 10, the API's pool size), `STATS_CACHE_TTL` (default `10m`; how long the API reuses stats computed from match data before querying Postgres again; must be positive), `REDIS_URL` (optional `redis://` URL for the shared stats cache below).

Personal Riot API keys expire every 24h — refresh `deploy/.secrets/riot-api-key.txt` (gitignored) before ingesting.

Background sync in dev: `docker compose -f deploy/docker-compose.yml --profile sync up -d --build riotsync` runs `riotsync` in a container (restarts unless stopped, runs as `APP_UID:APP_GID`, default 1000:1000, so it can read the chmod 600 key; key rotation needs no restart). It keeps running (and spending the key) after a reboot until stopped: `docker compose -f deploy/docker-compose.yml --profile sync stop riotsync` (`down` removes it). It waits for `migrate`, so the checkout's migrations must match the dev database's applied version (use `--no-deps` otherwise).

### Frontend (`frontend/`)
```bash
npm install
npm run dev      # Vite dev server on :5173, proxies /api to localhost:8080 (API_URL=http://localhost:<port> npm run dev to use another backend)
npm run build    # tsc -b && vite build
npm test         # vitest (pure frontend logic, e.g. src/planner/board.test.ts)
npm run assets   # download TFT icons + manifest from Data Dragon into public/tft/ (gitignored, ~100 MB; re-run after a patch)
```
Game icons are looked up through `src/assets/tft.tsx` (`GameIcon`, `GameLabel`, `lookup`), keyed by Riot API id (`TFT17_Jinx`, `TFT_Item_InfinityEdge`; Set 18 switched to a `DA_` prefix, e.g. `DA_Amumu18`, `DA_18_Elderwood`). Without downloaded assets the UI falls back to text names. Profile icons load from the Data Dragon CDN rather than being downloaded.

The live TFT set number is `CURRENT_TFT_SET` in `frontend/src/config.ts` — the only place to bump when a new set launches. The backend is set-agnostic (aggregation runs for every `tft_set_number` present in `matches`).

## Architecture

### Binaries (`cmd/`)
- **api** — HTTP server (`internal/apiserver`). Routes under `/api/v1/` for player profiles, player match history, match detail, leaderboard, and meta units/traits/augments; plus `/healthz`.
- **ingestcli** — bounded ingestion runs, safe under personal-key rate limits. Subcommands: `whoami`, `seed-leaderboard`, `crawl-matches`, `crawl-queue`, `aggregate`, `sync-setdata`.
- **aggregator** — recomputes the `meta_*_stats` tables from `match_participants`. Makes no Riot calls; can run frequently (e.g. as a CronJob).
- **riotsync** — background service (`internal/riotsync`) that pulls Riot data into Postgres on a schedule: leaderboard seeding, bounded `CrawlQueue` batches, Riot ID resolution and meta-stat aggregation, run one task at a time under its own single `RateLimiter` plus a `Throttle` transport capping its traffic at `RIOTSYNC_RATE_LIMIT_PER_SEC`/`_PER_2MIN` (default 10/s, 50 per 2 min) because it shares the key with the API server and the client's limiter syncs to the key's full budget. Runs are recorded in `ingest_runs`; a Postgres advisory lock allows one instance per database; it pauses after an expired key or rate-limit stop. Tuned with `RIOTSYNC_*` env vars (`RIOTSYNC_PLATFORMS`, `RIOTSYNC_SEED_INTERVAL`, `RIOTSYNC_CRAWL_INTERVAL`, `RIOTSYNC_NAMES_INTERVAL`, `RIOTSYNC_AGGREGATE_INTERVAL`, `RIOTSYNC_CRAWL_*`, `RIOTSYNC_NAMES_BATCH`, `RIOTSYNC_KEY_RETRY`). Pauses for Riot's `Retry-After` after a 429. The crawl queue is ordered by staleness first (never-crawled, then longest since crawled) with the tier priority only breaking ties, so every queued player gets a turn instead of the top tier refilling every batch; priority follows the current ladder in both directions (each complete seed sets it, and players who left the ladder drop to 0). A player whose crawl fails is backed off from (`ingest_puuid_queue.failures`/`next_attempt_at`, 2, 4, 8… minutes up to a day, `store.MarkCrawlFailed`) and the batch carries on; only an expired key, Riot being unavailable (`riotapi.ErrUnavailable`: 5xx or network failure after the client's retries) or a cancelled run aborts it (and backs nobody off), and a rate limit before Riot returned the id list leaves the player unmarked (neither crawled nor failed). Invalid `RIOTSYNC_*` values fail startup. Replaces the old ingestworker placeholder and the `ingest` compose service (use `--remove-orphans` when upgrading).

### Packages (`internal/`)
- **config** — env-var loader shared by every binary.
- **riotapi** — Riot API client, region routing, and `RateLimiter`. `KeySource` abstracts the key: `FileKeySource` re-reads the file on every use so keys can be rotated without restarting; `EnvKeySource` is fixed at startup.
- **ingest** — `seeder` (leaderboard PUUIDs → queue), `queue`, and `crawler` (fetch matches for queued PUUIDs).
- **aggregate** — `RecomputeAll` builds the meta stats tables.
- **store** — hand-written pgx queries (no sqlc/ORM, intentionally, while the schema evolves).
- **apiserver** — handlers, DTOs, router.
- **db/migrations** — sequential golang-migrate SQL files (`0001`…).
- **setdata** — static set data (units, traits, augments, items) from CommunityDragon, stored as per-version snapshots; see below.
- **settags** — empty, not yet implemented.

### Build advisor (Explorer)
`GET /api/v1/explore/suggest?set=&queue=&level=&have_unit=…&have_item=…` (`handlers_suggest.go`, pure logic in `internal/suggest`) answers "what can I build with what I hold right now". Inputs are the player's units and inventory (one `have_item` per copy; completed items or components). It takes the exact 3-item builds per unit (`store.MetaBuilds`, wider than the Meta page's) and comps (`comps.Build`, shared cache with `/meta/comps`) from real boards, then: `craft` decides which build items the inventory covers, from a whole item or two components (recipes = `Composition` of the newest set-data snapshot, cached; without a snapshot only whole items match), never spending a piece twice; `plan` greedily gives each unit its best-fitting build without double-spending items; `units` are per-unit alternatives against the whole inventory; `comps` are comps ranked by owned units on their board, with item fits. Units alone list their best builds (nothing makeable yet = aim-for builds, all missing); items alone (no `have_unit`) return `candidates`, the units whose builds the inventory fits best (API only; the panel doesn't show them, as `builds` already names the carriers), plus `builds` (real builds grouped by their items across every unit that carried them, stats combined, main carriers listed; same ranking as unit builds) and `crafts` (completed items held whole or makeable from two held components, with stats over the builds that include them), and `comps` become final boards for the items: comps ranked by how many of their carries' items the inventory makes, carries served in board order from one shared inventory so no piece counts twice (`internal/suggest/items.go`). Emblems and artifacts are treated as reasons to build a unit: a board unit with a real build that uses a held one takes that build first (`alt`, `enablers`: Master Yi with a Brawler Emblem), and a leftover emblem fits boards that play its trait (`emblems`, trait = the trait named like the emblem without " Emblem"). Boards rank by items made, then boards an emblem/artifact enables, then how many units the emblem's trait has, then fewest missing and sample-aware placement. Emblems are recipes too (Spatula/Frying Pan + component); artifacts only count when held whole. Frontend: `components/BuildAdvisor.tsx` in the Explorer; its lists are the `hu`/`hi` URL params.

### Data freshness (request-triggered Riot fetches)
- **Leaderboard** — `GET /api/v1/leaderboard/{platform}` re-seeds the platform from Riot (3 requests, `ingest.SeedLeaderboard`) when its snapshot is older than 2 minutes; a complete seed prunes players who left master+. Missing Riot IDs on the returned page are resolved in the background via account-v1 by-PUUID (`ingest.ResolveNames`). Each entry also carries `games` and `top4Rate` from Riot's league entry (in TFT its `wins` are top 4 finishes, `losses` the rest) and `stored`: 1st-place rate, top 4 rate and average placement over that player's stored ranked games of the newest set (`store.RankedBoardStats`, one query for the returned page; null without stored games). Riot has no 1st-place or average figure, so the page shows the stored sample size next to them. Refresh serialization is in `internal/apiserver/leaderboard_sync.go`.
- **Match history** — `GET /api/v1/players/{puuid}/matches?region=<platform>[&offset=&limit=]` pages a player's stored games newest first, each with its final board (units with stars and items, active traits with Riot's badge style; `store.PlayerMatches`). The first page (offset 0) starts a background sync (`ingest.SyncPlayerMatches`: ids + any unsaved matches from the last 20) when the player's history wasn't synced in the last 2 minutes. Sync time is `ingest_puuid_queue.last_crawled_at`, so viewed players also join the crawl queue. Pages are 20 games at offsets that are multiples of 20 (anything else is 400; `limit` can only shorten the first page), so a player has at most 25 older pages to fetch from Riot, one job each, instead of a job per (offset, limit) pair. An older page (offset > 0, at most 500) that isn't fully stored starts a background fetch of that page of Riot's ids (`ingest.SyncOlderMatches`, `GetTFTMatchIDsPage` with `start`); that job always reports incomplete so a finished page isn't refetched by every poll for a minute. `hasMore` = the page is full or still being fetched. Pages line up with Riot's because the newest page is synced first. Without `region` the endpoint is cache-only. `refresh=1` on the first page (the profile's Update button; it re-requests the profile too, but that is served from the database for an hour, so a changed name, icon or level shows up only after that) lowers the wait from 2 minutes to 20 seconds (`matchHistoryRefreshMin`, `syncDue`); a refresh sooner than that starts nothing and answers `refreshTooSoon`. The sync it starts also refreshes rank, so stats and the LP graph reload as games arrive.
- **Player stats** — `GET /api/v1/players/{puuid}/stats?set=[&queue=&level=]` (`handlers_player_stats.go`) never calls Riot: it runs the explorer query with `ExploreFilter.PUUID` (a board condition, so `baseline` stays everyone's) for summary, placement histogram and unit/item/trait breakdowns, plus `PlayerQueues`, `PlayerSets` and the player's own comps (`comps.Build` over their level 8+ boards, 2+ games). The profile page (`ProfilePage.tsx`, `components/PlayerStats.tsx`, `components/MatchHistory.tsx`) adds recent form from the first history page and a "vs meta" column from `/meta/builds`, and reloads stats when history pages bring new games. Patches and LP: Set 18 matches report no game version (`TFT Unreal Version ?.?.?.?`), so a game's patch comes from its date via `patch_calendar` (migration 0011; `setdata.SyncPatchCalendar`, run with every set data sync, reads each patch's Riot notes `datePublished` and takes the patch as live a day later; `setdata.PatchOfGame` prefers a real `<Releases/x.y>` version when present). Riot's match data has no LP either: `rank_snapshots` records a player's rank per queue whenever it changes — after each newest-games sync (`ingest.SyncPlayerRank`, one `tft/league/v1/by-puuid` request) and from every apex ladder refresh (`WriteLeagueSnapshot`) — and `internal/lp` attributes the LP difference between consecutive snapshots to the stored ranked games between them (exact for one game, a total over several shown on the newest; spans whose stored games don't match the record's game count are skipped). Snapshots are ordered by games played (wins + losses), not fetch time — the apex ladder lags the by-puuid lookup, so a ladder snapshot fetched seconds later can be an older standing — and placed among the stored games (by end time, `game_datetime` + length) by game count, anchored to the games that ended within `clockSlack` (1h) of the fetch; a count drop of more than 5 games starts a new season. LP therefore exists only from a player's first snapshot on. History pages carry `patch`, `lp` and (first page) `ranks`; stats carry `patches` (by patch with known LP). The profile groups history rows under patch headers. `GET /api/v1/players/{puuid}/ranks` returns `history` (snapshots per queue with `value`, `lp.Value`) and `estimated`: for Ranked, the standing after each stored game of the current set before the first snapshot, worked back from it with a typical LP per placement (`lp.EstimateBefore`: +40/+30/+20/+10/−10/−20/−30/−40; real gains depend on hidden MMR, so it only sketches the climb). The profile's LP history panel (`components/LPHistory.tsx`, `LPChart.tsx`) draws both as one step line (LP holds between points) — recorded solid, estimated dashed with a legend and "estimated" in tooltip and table — laid out at the container's pixel width, with a hover tooltip and a table view. "Load whole set" (`components/SetBackfill.tsx`; `POST`/`GET /api/v1/players/{puuid}/backfill?region=`, `internal/apiserver/backfill.go`, `ingest.BackfillSet`) lists the player's match ids since the current set's start (patch calendar, minus a day; Riot's `startTime` filter, 200 ids per request) up to 500, then fetches every one not stored, waiting out 429s rather than stopping. The endpoint is public and each load costs hundreds of requests, so: only players with stored games can be loaded (404 `unknown_player`); loads run one at a time server-wide with a 10-minute gap after any load ends (409 `busy` with `Retry-After`), so loads for different players can't be chained; a load's requests are paced 2.4 s apart (`backfillPace`, half a personal key's 100 per 2 minutes) so live pages and riotsync keep headroom instead of queueing behind it (500 games take ~20 minutes); a finished load isn't rerun for 10 minutes and a failed one isn't retried for as long (409 `cooldown`); progress (found/missing/fetched) is polled and the stats reload every 20 games. Match history mode tabs (All / Ranked / Double Up …, with counts) filter the loaded games in the browser: Riot's match id list can't be asked for one queue, so server paging stays unfiltered and "Load more" keeps paging through every mode. Riot reports summoner level 1 for many accounts since TFT's own client, so the header hides level 1. Double Up partners: Riot's Set 18 match data has no team field (Set 17's `partner_group_id` is gone), but a team's two players always take a consecutive placement pair (1-2, 3-4, …; it matched `partner_group_id` in every Set 17 game and pairs share their elimination time in Set 18), so `store.PlayerPartners` and the history rows (`partner`, `team` = (placement+1)/2) pair players that way, Double Up queue (1160) only. The match page groups a Double Up game's players into these teams (`partner_group_id` when present). Partner names come from `accounts` when resolved, else from the match payload's `riotIdGameName`/`riotIdTagline`. Stats carry `partners` (games, average team place, team top 2 rate) unless the queue scope leaves out Double Up.
- **Sessions** — stats also carry `sessions` (`internal/sessions`, pure): the player's set/queue-scope games split into play sessions at 30-minute breaks (next start minus previous end), with results by game number in the session (5+ grouped) and for the next game after a top 4, a bottom 4 and two bottom 4s in a row (tilt). Built from stored games only, so an unstored game can split a session; "Load whole set" fills them in. Shown as the Sessions block in the profile's Stats panel (rows under 3 games dimmed).
- **Lobby strength** — how strong a game's opponents were, from their Ranked standing around it (`store.LobbyPlayers`): the rank snapshot nearest the game within 14 days (`LobbyRankWindow`; two index-ordered lookups, before and after), else the player's current apex ladder entry, flagged `current` (snapshots only exist since 2026-10-06, so older games lean on today's ladder). Ranked is used for every queue, Double Up included (its own standings are rarely known). `internal/lobby` (pure) averages the opponents' `lp.Value` (the player and, in Double Up, their teammate excluded) and rates a game only when at least half of them are known. Master, Grandmaster and Challenger share one LP ladder and the GM/Challenger cutoffs move daily (they hold a set number of the region's top players), so an apex average is named by the platform's current cutoffs: `store.LadderCutoffs` takes the 5th percentile of each tier's LP in `league_entries` (robust to players who dropped since Riot's daily tier update), and `lobby.TierOf` returns MASTER/GRANDMASTER/CHALLENGER (empty below Master or without a stored ladder, when the page says "Master+"). History rows carry `lobby` (value, tier, known, current, opponents); `GET /api/v1/matches/{matchId}/lobby` (stored data only) returns each ranked participant's standing (`players`: tier, division, LP, `value`, `current`) and the average over them (`average`, `averageTier`, `known`, `total`). Frontend: "lobby ≈ …" on history rows; on the match page, "Lobby ≈ … (N of 8 players ranked)" in the header and each player's rank next to their name ("(now)" when from today's ladder). A split of results by lobby strength was tried and dropped as not useful.
- **Player advice** — `GET /api/v1/players/{puuid}/advice?set=[&queue=&level=]` (`handlers_player_advice.go`, pure logic in `internal/advice`, never calls Riot) compares the player's `MetaBuilds` (scope + `PUUID`) with everyone's (the advisor's cached `builds-wide` result): units they do worse/better with than *expected* — everyone's average with the unit shifted by the player's edge (their average minus everyone's), so a strong player still sees their weak spots — and, for their most played units, their usual exact build (3+ games) next to a build everyone does clearly better with (both sides are everyone's games, so it doesn't depend on the player's skill). Notes need a minimum gap and 1.5 standard errors (placement SD ≈ 2.29) so a few lucky games don't count; a suggested build needs 30+ boards and is picked by its pessimistic average. The profile's Advice panel (`components/PlayerAdvice.tsx`) is disabled for now (not useful enough yet), and the route is unregistered while it is (it scans everyone's boards per scope); to bring it back, register the route in `router.go` and render the panel in `PlayerStats.tsx` after the Stats panel.
- Background runs go through `backgroundJobs` (`internal/apiserver/background.go`): one run per key at a time, a 1-minute cooldown after incomplete/failed runs, and the last error surfaced as `stale`/`staleReason`. Responses carry `resolving`/`refreshing` flags; the frontend polls every 3s while set.

### Set data and generated patch notes
`internal/setdata` downloads CommunityDragon's TFT export (`raw.communitydragon.org/<channel>/cdragon/tft/en_us.json`, ~25 MB; channel is `latest` or a patch archive like `16.18`), extracts the set's standard-mode entry (`TFTSet<N>`), renders description templates (`@Var@`, `@Var*100@`, `%i:scaleAP%`, `<row>` breakpoints) to plain text, and stores the result in `set_data_snapshots`, one row per content version. Patch notes are not scraped: `GET /api/v1/sets/{set}/patches` diffs each snapshot against the previous one (`setdata.Diff`). `GET /api/v1/sets/{set}/data[?version=]` serves a snapshot.
- Updating: the API server syncs `latest` at startup and every `SETDATA_SYNC_INTERVAL`; `ingestcli sync-setdata [--set N] --versions 16.17,16.18,latest` syncs or backfills manually. A sync skips versions already stored and builds whose data is identical to the previous snapshot.
- Variables CommunityDragon couldn't name are keyed by FNV-1a of the lowercased name (`{b027c2f9}`); `namedValues` maps them back using names found in the description.
- Set 18 moved champion spell math and augment reward logic into the new client; neither is in CommunityDragon's export or `map22.bin` (67 of 69 Set 18 spells have only placeholder `DataValue`/`OtherValue`, on live and PBE). Ability text comes from tactics.tools instead (`overrides.go`): `ap.tft.tools/static/s<N>/en.js` holds fully rendered tooltips keyed `<apiName>_desc`; it's fetched with each set data sync into `set_text_overrides`, tagged with the newest snapshot version, and applied at serve time only to that version and only where our text has unknowns, with `descSource` attribution. Remaining unresolved variables render as `[[Label]]` (`unknownValue`, e.g. `@MagicDamageCalc1@` -> `[[Magic Damage]]`), which the frontend styles as an unknown-value chip. Unit stats and trait/augment/item values are exact.
- Live in-game values have no static text: League-client counters (`@TFTUnitProperty...@`) and the new client's runtime placeholders (`{ItemTags.Deathblade.DeadlierBladeStacks}`, `{Augment.Variant.MagicRoll.Reward}`; dotted paths only, so CommunityDragon's `{0f90e7a4}` hashes never match). `stripTrackers` drops parentheticals around them and lines where one is a label's value, and otherwise removes just the placeholder.
- Augment reward tables (`internal/setdata/rewards/set<N>.json`, embedded) are hand-transcribed from Little Buddy Bot because Set 18's reward logic isn't in any export. They cite a per-augment `sourceUrl` and `updated` date, key on explicit `apiNames` (the set's own `DA_*` augments), and are attached when serving (`AttachRewards`), never stored in snapshots. Only facts are transcribed (never their images); icons that couldn't be identified are marked with a footnote instead of guessed. The loader validates the file at startup (row/column counts, duplicates, required source fields).
- The site footer carries Riot's required "Legal Jibber Jabber" notice; keep it on every page.
- Set pools come from Riot's set definition, not name heuristics (`pools.go`): `map22.bin.json` (~70 MB, streamed) has `TFTSetData` `TFTSet<N>` -> `itemLists`; the set's own lists are `Set18_Items` (156 items), `Set18_Items_Augments` (250) and `TFTSet18_Items_Charms` (343 Wisps), while shared lists (`Common_Items`, which holds debug items, legacy copies and other modes' items) are ignored. A sync fails if pools can't be read, so all snapshots stay extracted the same way. Set 18's own items have no description in the export; they're kept and get text from tactics.tools overrides. Without pools (older sets) the heuristics below apply.
- Augments (no-pools fallback): when a set has `DA_*` augments, only those are kept (`dedupeAugments`). The ~340 legacy `TFT*_Augment_*` entries in Set 18's list aren't live — every 18.2 official augment change landed on the `DA_` id while legacy copies stayed frozen, and Cursed Crown's removal (18.3) dropped only its `DA_` id. Patch notes pair entities by id, then by unique name (catching id swaps; only fields both sides define are compared), and report renames.
- Generated patch notes miss balance changes not reflected in the exported files (most of 18.3's), so each patch links Riot's official notes (`TFTPatch`, `OfficialNotesURL`; add a set's first game patch to `firstGamePatch` when it launches).
- Riot's set augment list also carries legacy copies (`TFT_Augment_MagicRoll` "A Magic Roll" next to `DA_MagicRoll` "Magic Roll"); `dedupeAugments` drops a legacy augment when a set-specific one has the same name (case-insensitive, ignoring a leading article). Same-named set-specific augments are distinct variants and are kept.
- Set 18's remaining `DA_*` items are Wisps (the set mechanic) and live in `SetData.Wisps` / patch-note category `wisp`, not `Items`.
- Snapshots hold extracted data, not the raw export, so changing the extraction (new fields, filters) makes old and new snapshots differ in shape and produces spurious diffs. After such a change, delete the set's rows from `set_data_snapshots` and backfill again with `sync-setdata`.

### Stats explorer
`GET /api/v1/explore` (`handlers_explore.go`, `store/explore.go`) filters player boards (`match_participants` joined to `matches`) by AND-ed conditions: units (`unit=ID[*minStar][:I1,I2]`; star and items must hold on the *same* unit copy), items anywhere, traits by `num_units` (`trait=ID[*min[-max]]`; an exact tier is `min..nextBreakpoint-1`, e.g. Juggernaut tier 2 = `*4-5`), queues and level range. It returns summary + placement histogram, a baseline (same set/queues/levels without board conditions), breakdowns of units/items/active trait tiers on matching boards (each board counted once), and per unit condition the items held and best star level on matching copies (each board counted once, so counts line up with Boards everywhere). The UI groups trait rows by trait with one row per tier; tier N maps to the set data's Nth breakpoint (`tier_current` counts breakpoints reached; repeated breakpoints like Rival's `1, 1, 2` are clamped). All values are bound parameters; ids must match `^[A-Za-z0-9_]{1,80}$`, max 6 conditions per kind. JSONB columns go through `arrayOr` so a malformed row can't fail a query; unit conditions add a `units @> ...` containment test served by the GIN index on `units` (migration 0004; 0013 dropped the duplicate 0009 added, plus indexes no query uses: `match_id` (covered by the unique `(match_id, puuid)`), `placement` and `augments`). `/explore/options` lists what occurs in a set's data so the UI only offers matchable conditions. The page (`ExplorerPage.tsx`) keeps the search in its URL in the API's own format and waits for options (which pick the default ranked queue) before searching. Augments and Set 18 damage aren't filterable: Riot's match data has no augments and reports 0 damage.

### Meta page
`GET /api/v1/meta/builds` (`store/meta.go`) computes, live over the same scope as the explorer (set/queues/levels; board conditions are rejected), each unit's stats and pick rate, its most common exact builds (the unit copy's three items as a sorted multiset, duplicates kept; one count per board; only builds seen `metaMinBuildGames`+ times) and its most-held items. The page (`MetaStatsPage.tsx`) shows unit cards (cost filter, search, sort by games or by average with a 10-game minimum) and a Traits tab reusing the explorer's tier-grouped table (`components/stats.tsx`, shared with `ExplorerPage.tsx`). Builds link to the explorer as `unit=ID:I1,I2,I3`; explorer unit-item conditions count duplicates (two Archangel's must both be present) so those numbers match. The old precomputed `meta_*_stats` tables/endpoints remain (the `aggregate` job still fills them) but the UI no longer uses them.

### Comps
`GET /api/v1/meta/comps` loads final boards (player level 8+, set/queue scope; `store.FinalBoards`) and groups them with `internal/comps` (pure Go, no DB): distinct exact unit sets are taken most-played first, and each joins the comp whose *anchor* board it overlaps most (Jaccard >= 0.6) or anchors a new one, so every comp is built around a board people actually ran. Per comp: stats and play rate, the anchor board with each unit's most common star level and most common real item set (3+ copies and 5%+ of copies; tanks with scattered items show none), stats for boards that ran exactly the anchor, variants (other exact boards in the comp, as add/remove swaps — "level up: +X" when only adding) and flex units (off-anchor units on 15%+ of the comp's boards). Comps under 5 boards are dropped. `/meta/builds` and `/meta/comps` scan every board in scope, so results are cached per (kind, set, queues, levels) for `STATS_CACHE_TTL` (10 minutes by default; `Server.StatsCacheTTL`, applied to `Server.meta` and `Server.stats` in `NewRouter`) (`Server.meta`, a `resultCache` from `internal/apiserver/result_cache.go`: concurrent misses share one computation, at most 2 different keys compute at once (a caller that leaves while waiting for a slot doesn't fail the callers sharing its entry; a panicking computation becomes an error), errors aren't cached, except one that took 5+ seconds to arrive (the statement timeout): that is answered again for a minute so a computation that outgrew the timeout runs once a minute rather than for every visitor, and computations taking 1s+ are logged; at most 64 entries; queue params are capped at 6 and `set` at 100). The Meta page's default tab shows them; names come from traits the anchor invests in (tier 2+ or 3+ units), else its itemized carries.

`/players/{puuid}/stats` takes its everyone's baseline from the same cache (`Server.scopeBaseline`, one entry per set/queues/levels, passed to `Explore` through `ExploreFilter.Baseline`) so only the player's own indexed boards are queried per request. `/explore` searches have a cache of their own (`Server.explore`; key = set, sorted queues, levels and every condition in the request's order), in the replica's memory only and with up to 4 searches computing at once: every distinct search misses, so they get their own slots (a burst of searches can't queue the cheap entries behind it) and stay out of Redis (one-offs would push out the entries worth sharing). `/explore/options` and the scope baselines use `Server.stats`. Each cache holds at most 64 entries and evicts the oldest.

**Shared cache (Redis, optional).** With `REDIS_URL` set, the API replicas keep explorer options, scope baselines, meta builds/comps and advisor-input results in Redis (`internal/rediscache`; `apiserver.SharedCache`, `shared_cache.go`) with `STATS_CACHE_TTL` as the entry TTL, so one replica's computation serves all and the database is scanned about once per TTL for the whole fleet. Each replica's in-process `resultCache` stays in front (single-flight, compute limits) but shortens to 1 minute so freshness is governed by the Redis TTL (worst case about TTL plus 1 minute). On a miss a replica takes an advisory Redis lock (`SET NX`, 60s) so replicas don't compute the same stat at once; the others poll up to 10s for its result, then compute anyway. Values are JSON (`cached[T]` needs `T` to survive a round trip; bump `keyPrefix` in `rediscache` when a cached shape changes). Redis is never required: errors or an absent entry mean "compute here", and a failing Redis is skipped for 30s (`sharedBreaker`) so it costs one slow request, not a timeout per miss. Set data, patch notes, planner codes and advisor item recipes stay in memory only. Compose: `redis` in the dev file (127.0.0.1:6379) and in the prod file (password `REDIS_PASSWORD`, no persistence, 128mb LRU, internal network only).

The explorer hides results until a condition is set (otherwise it repeats Meta) and leaves condition rows (chosen units, required items, chosen traits) out of its breakdowns.

### Board planner
`/planner` (`pages/PlannerPage.tsx`, model in `planner/board.ts`, frontend only) lets a user place units on the 4x7 hex board (pointy-top hexes, odd rows shifted half a hex, laid out on a 15-column CSS grid sized with container query units; the clipped button is the hit area and slots are `pointer-events: none` so overlapping corners don't steal clicks; unit art fills the hex, cost sets the edge colour, stars on top, items on the lower edge) (drag to move or swap; select a unit then click an empty cell to move it; right-click removes), set star levels, up to 3 items per unit, three augments, the player level and a title. Units are picked from a compact icon grid grouped by cost (details on hover: traits, stats, ability) and items from a grid like the in-game combination chart (`components/PickTables.tsx`): the set's components along both axes, the item two components make in the cell where they meet (completed items and Spatula/Frying Pan emblems, mirrored), and everything with no component recipe (artifacts, radiants, emblems from other sources) in separate sections below; hover shows kind, recipe and text. Components themselves aren't holdable. Augments sit in three stage slots (first 2-1, second 3-2, third 4-2). Which augments a slot offers comes from `planner/augmentStages.data.json`: per augment its tier and the stages it can be offered at, scraped from tactics.tools' augment list (`npm run augment-stages`, `scripts/fetch-augment-stages.mjs`; it reads the page's dimmed stage chips and fails loudly if the markup changes; re-run after patches). Our set data has no stage info, and 29 augments have tier 0 there (unknown), so `augmentTier` falls back to the scraped tier; an augment missing from the scraped data is offerable everywhere, one listed with no stage in no slot. Edits go through `update(edit)` which applies them to the URL's current board, so rapid clicks don't overwrite each other. Nothing is stored server-side: the whole board is the page URL (`set`, `t`, `lv`, `a1`/`a2`/`a3=<augment>` (older repeated `a=` links still load, filling slots in order) and `u=<unitId>.<star>.<pos>[.<item,item,item>]`, pos 0-27 row-major, row 0 the front line), so sharing is copying the link. A link is untrusted input: `decodeBoard` validates id shape, bounds positions/stars/counts, ignores duplicate cells, and cleans the title (React escapes it on render); once set data loads, `sanitize` drops units/items/augments the set doesn't have (items must also be holdable kinds: no components or consumables)  and the page says how many. Traits: each distinct unit counts once; an emblem adds its trait (item name minus " Emblem" = trait name) to a holder that lacks it; tiers come from the set data's breakpoints. Gold cost counts a 2-star as 3 copies and a 3-star as 9. Item rules (`canHoldItem`, in `planner/board.ts`): an emblem can't go on a unit that already has its trait (its own, an evolved one, or from another emblem it holds, which also rules out the same emblem twice); blocked emblems stay visible, dimmed, with the reason in the hover card, and `dropRedundantEmblems` removes ones that became redundant (a Lux's chosen trait, an evolved trait) after every edit and when a link loads. Right-clicking an item on the board takes it off. Units that take extra team slots (Set 18's Elder Dragon: the Apex Predator trait says "Elder Dragon takes up 2 team slots and grants +2 to the Riftbeast trait") are read from that text (`buildSlotRules`): the unit counter counts slots, not units, and the unit counts as that many (2) for the named trait. Items whose text says "+N maximum team size" (the Tactician's Crown/Cape/Shield; read from the description, each counted, stacking is an assumption) raise the unit limit shown next to the level. Units that choose a trait (Set 18's Lux: "Lux" plus "Lux (Coven)", "Lux (Fae)"... as separate set-data units) are recognised by the name pattern "<base> (<trait>)" (`buildFormIndex`), shown once in the unit grid, and get a Trait menu in their editor that swaps the placed unit for that form (the link stores the form's apiName); all copies of such a unit share one trait (`setForm` changes every copy, `normalizeForms` makes a newly added or loaded copy agree with the front-most chosen one); the chosen trait counts twice for trait bonuses, as the Avatar trait says, and the in-game code uses the base unit. Units that gain traits by evolving (Kha'Zix: "your choice of Executioner, Rapidfire, Ravager, or Spellweaver") are found by reading that sentence from the trait text (`buildTraitChoices`); the placed unit gets checkboxes for up to that many traits (`PlacedUnit.extra`, stored as a fifth `.`-field of the `u` parameter, e.g. `u=DA_18_KhaZix.1.21.<items>.<trait apiNames>`), each counting once toward its trait; links are cleaned of traits the unit can't have. The in-game Team Planner's copy/paste code is built in `planner/teamCode.ts` (`01`/`02` prefix, 10 slots of 2/3 hex digits, `TFTSet<N>`; units only, no positions/items/stars/augments; the format is community reverse-engineered, Riot doesn't document it) from per-champion numbers that CommunityDragon publishes (`tftchampions-teamplanner.json`, `team_planner_code`; Set 18's start at 1001, hence 3 digits). The API serves them as `GET /api/v1/sets/{set}/planner-codes` (`setdata.FetchPlannerCodes`: one download for all sets, 4 MB cap, cached 5 min in `Server.sets`; `Server.Source` points tests at a fake), so the browser never talks to CommunityDragon (the CSP wouldn't allow it); the download has its own 15 s timeout (the file is ~65 KB, not the 25 MB export `DefaultSource` is sized for) and a failure is remembered for 30 s so a down source isn't retried per request. The planner can also load units from a pasted code (the set is checked before the unit numbers). Tests: `npm test` (vitest, `planner/board.test.ts`, `planner/teamCode.test.ts`).

### Hardening (public, unauthenticated API)
The API has no auth, so the risks are abuse of the shared Riot key and resource exhaustion. Keep these properties when adding endpoints:
- **Validate ids before use** (`internal/apiserver/validate.go`): PUUIDs, match ids and Riot IDs are checked before they reach the store, `backgroundJobs` or Riot. `riotapi` also escapes every caller-supplied path segment (`pathSegment`, which refuses `.`/`..`), so input can't steer a keyed request to another Riot endpoint. `ingest.SyncPlayerMatches` stores and queues a PUUID only after Riot returns its match ids.
- **Bound per-key state**: `backgroundJobs` keeps only running jobs (max 32 at once; past that `start` reports the job as pending so the client keeps polling and retries) and failures within their cooldown (pruned past 1000); `resultCache` holds at most 64 entries; the 404 memory at most 10k.
- **Live Riot fetches on the request path** (match detail, profile) go through `Server.live` (`live.go`): at most 4 in flight (503 + `Retry-After` otherwise), and Riot 404s are remembered for 10 minutes.
- **Errors**: database failures go through `writeDBError` and unexpected Riot errors through `writeRiotError`; both log the detail and return a generic message. Only input-validation messages (ours) reach clients verbatim.
- **Size and time limits**: Riot responses are capped at 4 MB, set data downloads at 200 MB (export), 500 MB (streamed map) and 32 MB (overrides); `cmd/api` sets `http.Server` timeouts (`WriteTimeout` 45s must stay above nginx's 30s proxy timeout).
- **Caching**: set data and patch notes are built once per set into a `setBundle` and cached 5 minutes (`Server.sets`); `{set}` is capped at 100. Snapshots in the bundle are shared, so handlers must not mutate them. Meta and set responses send `Cache-Control: public, max-age=300`.
- **nginx** (`frontend/nginx.conf.template`, `frontend/security-headers.conf`): per-IP `limit_req` on `/api/` with a tighter zone for `/api/v1/(matches|players)/`, `server_tokens off`, CSP and other headers (any `location` with its own `add_header` must `include` the headers snippet), and `X-Forwarded-For` set to the peer address only. The image is `nginx-unprivileged`, still listening on port 80: Docker lets non-root processes bind low ports in a container (`net.ipv4.ip_unprivileged_port_start=0`, set explicitly in the prod compose file), so no capability is needed.
- **Compose**: app containers use `cap_drop: [ALL]`, `no-new-privileges`, `read_only` with tmpfs, and memory limits; the frontend's `/etc/nginx/conf.d` tmpfs must be owned by uid 101 or nginx starts without its config. Dev Postgres listens on 127.0.0.1 only.
- API-provided links in the frontend go through `safeHref` (https only). Riot ID lookups are case-insensitive (migration 0010).

### Key invariant: one rate limiter per process
Exactly one `riotapi.Client`/`RateLimiter` is built at startup and injected (e.g. into `apiserver.Server`). Handlers and other code must never construct their own client, so live fetches and ingestion can't jointly exceed Riot's rate limits.

### Deploy
`deploy/docker-compose.yml` is local dev (Postgres + migrations). `deploy/docker-compose.prod.yml` is the production stack: images from `Dockerfile` (backend: `api`/`ingestcli`/`aggregator`/`riotsync`; `scripts/ingest-loop.sh` is the older shell-loop alternative to riotsync), `frontend/Dockerfile` (unprivileged nginx on port 80; `nginx.conf.template` proxies `/api` to `API_UPSTREAM`; icons fetched at build unless `FETCH_ASSETS=0`) and `deploy/migrate/Dockerfile` (migrations baked in). The `backup` service runs `scripts/pg-backup.sh --loop` (a custom-format `pg_dump` every `BACKUP_INTERVAL_SECONDS`, default a day, into `BACKUP_DIR`, newest `BACKUP_KEEP`=7 kept; `scripts/pg-restore.sh <dump> [db]` restores one, verified by restoring a dump into a scratch database and comparing row counts); copy `BACKUP_DIR` off the host, a dump next to the database doesn't survive losing the machine. The Riot key is a Compose secret mounted with host permissions, so backend containers run as `APP_UID:APP_GID` (the key file's owner) and the key stays `chmod 600`. Dockerfiles avoid BuildKit-only syntax (no buildx on the dev machine).
